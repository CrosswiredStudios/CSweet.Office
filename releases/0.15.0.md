# Office 0.15.0

- The Linux development guest image includes the `sgrep` 0.3.0 semantic code search command at
  `/usr/local/bin/sgrep`, built at image construction from source revision
  `dde0c13c8d6081f9c6d6d1d33580eebf1034aecf` with a pinned Rust 1.90.0 toolchain. The Rust toolchain,
  Cargo cache and sources are removed before the image is measured.
- The image bakes the code and text embedding models and the tree-sitter parsers for C, C++, C#, Go, Java,
  JavaScript, Python, Rust, TSX and TypeScript under `/usr/lib/csweet/toolchains/sgrep`, read-only.
  `versions.json` there records the pins and `env` records the runtime settings: agents run `sgrep` with
  `HF_HUB_OFFLINE=1`, the two baked cache paths, and `SGREP_CACHE_DIR` on writable workload scratch.
  Searches need no network and download nothing at run time.
- Image construction fails unless an unprivileged offline search over a polyglot fixture succeeds from the
  read-only caches. The public-internet certification probe additionally runs `sgrep --version` and one
  offline JSON search under its existing `developmentToolchain` check; the certification suite stays
  `csweet-hardware-vm-smoke-v16`.

Guided setup fixes:

- The Office installer waits up to 10 minutes (`-EnrollmentTimeoutSeconds`, 60–840) for the Office service's
  first enrollment, instead of 60 seconds, and keeps the setup progress fresh while it waits. The service
  verifies the multi-GB guest image before it claims, which took 70–125 seconds on a development host, so the
  old wait failed a healthy install and C-Sweet then revoked the connection code just before it was used.
  The installer still stops at once when the service reports an enrollment error.
- The Office service never retries a connection code that Headquarters rejected as invalid, expired or already
  used. It deletes the code, records `enrollment-rejected.json` in its state directory, logs the rejection
  once, and waits quietly for the installer to supply a new code. Network and transport errors keep retrying.
- RuntimeHost hashes the guest image once per probe and checks both its pinned digest and its signature
  against that pass, halving the time before the service's first claim. Verification is otherwise unchanged
  (`SEC-INV-10`).
- Guided setup reuses this computer's own certification of a byte-identical guest image, Hyper-V helper,
  guest probe and certification runner from the last 24 hours, so a reassign, repair or retry no longer boots
  the certification VMs again. Records are administrator-only and re-hashed before reuse; any changed input,
  stale record or `-Recertify` certifies again.
- Source guest-image builds use the selected Office CPU budget (capped at 4 vCPUs) instead of two, and the
  hosted release build gives `virt-customize` up to 4 vCPUs instead of one.
- After the Hyper-V restart, setup says to choose Continue setup in C-Sweet instead of claiming it resumes on
  its own. Requires the matching C-Sweet change, which relaunches the same session with a fresh one-use
  handoff; older C-Sweet builds still show the restart message.

The certification, signing, enrollment-token and Headquarters-trust rules are unchanged. Not yet verified on a
real host: the enrollment wait, the rejection marker and certification reuse need one guided install and one
reassign on Windows.

This changes the guest image and invalidates the development image fingerprint. Rebuild the guest image,
then certify and development-sign it on each destination host before installation; hosted bundles remain
development bundles. Drain the Office and wait for zero active assignments before an identity-preserving
upgrade. Workload isolation and the workload environment allow-list are unchanged (`SEC-INV-21`); the
sgrep settings are passed by the agent to its own child process. Image builds now need network access to crates.io, Hugging Face and the
tree-sitter-language-pack GitHub releases.
